# Walkthrough: the first hour

This walkthrough shows what the platform does by using it. You will send one order by hand, read its
trace span by span, look at the metrics it produced, and then run two experiments and read their
verdicts. It takes about 30 minutes.

**Before you begin:** the platform must be running. If it is not, follow the
[setup guide](setup-guide.md) first (`uv run platformctl bootstrap`). All commands run from the
repository root in a bash shell; on Windows, Git Bash works.

---

## Step 1 — Confirm that everything is running

```bash
uv run platformctl status
```

The important part of the output lists every workload and whether it is ready:

```text
==> Workloads
    gateway-system         deploy/kong-controller                1/1 ready
    gateway-system         deploy/kong-gateway                   1/1 ready
    transaction-platform   deploy/fraud-service                  2/2 ready
    transaction-platform   deploy/inventory-service              1/1 ready
    transaction-platform   deploy/keycloak                       1/1 ready
    transaction-platform   deploy/order-service                  1/1 ready
    transaction-platform   deploy/payment-service                1/1 ready
    transaction-platform   deploy/shipping-service               1/1 ready
    observability          deploy/jaeger-collector               1/1 ready
    observability          deploy/jaeger-query                   1/1 ready
    observability          deploy/prometheus-server              1/1 ready
    observability          sts/opensearch-traces                 1/1 ready
==> Experiments
    experiment lock: free
    every recorded run was restored
```

Twelve workloads in three namespaces: the gateway, the application with its identity provider, and
the observability stack. FraudService runs two replicas; everything else runs one.

## Step 2 — Send one order by hand

Every request needs a token from Keycloak. The platform's automation client is called
`scenario-runner`; its secret was generated during bootstrap and lives in a Kubernetes Secret.

```bash
# Windows' curl needs --ssl-revoke-best-effort to accept the local certificate authority;
# on Linux and macOS leave the variable empty.
TLS="--cacert .local/pki/ca.crt --ssl-revoke-best-effort"

SECRET=$(kubectl -n transaction-platform get secret keycloak-clients \
  -o jsonpath='{.data.scenario-runner}' | base64 -d)

TOKEN=$(curl -s $TLS \
  -d grant_type=client_credentials -d client_id=scenario-runner -d "client_secret=$SECRET" \
  https://localhost:9443/realms/transaction-platform/protocol/openid-connect/token \
  | uv run python -c "import json,sys; print(json.load(sys.stdin)['access_token'])")
```

Now place an order for two units of `SKU-1001`:

```bash
curl -i $TLS -X POST https://localhost:8443/orders \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "X-Debug-Trace: true" \
  -d '{"items":[{"sku":"SKU-1001","quantity":2}],"paymentToken":"tok_test_approved","shippingZone":"domestic"}'
```

A successful response looks like this (body shortened):

```text
HTTP/1.1 201 Created
RateLimit-Limit: 30
RateLimit-Remaining: 29
Location: https://localhost:8443/orders/01a0b3d2-c8df-77ee-90fb-1dfd6b3243a9
X-Correlation-ID: 4abb66f0-fe6f-4969-9aa5-51879d9fd853
traceresponse: 00-27e46ee2327d0884c4e063e215fa492a-fbc22c6d7ae4ed8a-01
X-Kong-Request-Id: b0030a32e2d9af175b958f6f2921d033

{"orderId":"01a0b3d2-…","state":"Completed","totalAmount":25.0,"currency":"EUR",
 "stateHistory":["Pending","InventoryReserved","PaymentAuthorized","ShipmentCreated","Completed"], …}
```

What each part tells you:

| Part | Meaning |
| --- | --- |
| `201 Created`, `state: Completed` | All four steps succeeded |
| `RateLimit-*` | Kong's rate limit: 30 requests per second per client, 29 left in this second |
| `Location` | The public URL of the new order |
| `X-Correlation-ID` | A human-friendly id for this request, generated by Kong |
| `traceresponse` | The W3C trace id of this request — the middle part, `27e46ee2…a492a` |
| `X-Kong-Request-Id` | Kong's own request id, also recorded on the spans |
| `stateHistory` | Every state the order passed through |

The `X-Debug-Trace: true` header asks the platform to keep this trace regardless of sampling.
Only callers with the `traces.debug` permission may do that; `scenario-runner` has it.

## Step 3 — Read the trace

Open Jaeger (the command keeps running until you press Ctrl+C):

```bash
uv run platformctl ui jaeger
```

Browse to `http://127.0.0.1:16686/trace/<trace id>`, using the trace id from `traceresponse`. The
trace appears about 35 seconds after the request: the Collector waits 20 seconds for all spans of a
trace before deciding to store it ([sampling.md](sampling.md)).

Jaeger's header summarises the trace — for the order above: **Duration 20.4 ms, Services 6,
Depth 7, Total Spans 16**. The span tree underneath looks like this:

```text
kong                                       kong-gateway        20.4 ms
└─ kong.balancer                           kong-gateway        19.0 ms
   └─ POST /orders                         order-service       17.1 ms
      └─ order.transaction                 order-service       15.7 ms
         ├─ inventory.reserve              order-service        5.8 ms
         │  └─ POST                        order-service        5.1 ms   (one HTTP attempt)
         │     └─ POST /inventory/reservations   inventory-service  0.9 ms
         ├─ fraud.evaluate                 order-service        5.4 ms
         │  └─ POST                        order-service        4.9 ms
         │     └─ POST /fraud/evaluations        fraud-service      0.7 ms
         ├─ payment.authorize              order-service        4.8 ms
         │  └─ POST                        order-service        4.3 ms
         │     └─ POST /payments/authorizations  payment-service    1.6 ms
         └─ shipping.create                order-service        4.6 ms
            └─ POST                        order-service        4.2 ms
               └─ POST /shipments                shipping-service   1.3 ms
```

How to read it:

- **The root span belongs to Kong.** Every trace starts at the gateway, never at the client
  ([gateway.md](gateway.md)).
- **`order.transaction` is the business view.** Its four children are the business steps. Below each
  step, the `POST` client span is one HTTP attempt, and below that is the dependency's own span. (The
  small number Jaeger shows next to a span name is its number of child spans.)
- **Inventory and fraud overlap in time.** In the timeline, the fraud check starts while the
  inventory reservation is still running, and payment starts only after both have finished. The
  trace checks verify this ordering automatically.
- **Every .NET span names its pod and node.** Click a span to open its details: the resource
  attributes Jaeger lists for the span's process include `k8s.pod.name`, `k8s.node.name`,
  `k8s.deployment.name` and `k8s.namespace.name`.
- **The state changes are events.** Open the details of `order.transaction` to see its four
  `order.state_changed` events, from `Pending → InventoryReserved` to `ShipmentCreated → Completed`,
  plus the attributes `order.id` and `order.state`.

The first request after a restart is much slower (a few hundred milliseconds instead of about 20),
because the services compile their code on first use.

## Step 4 — See the numbers behind the traffic

Still in Jaeger, open the **Monitor** tab and select `order-service`. It shows request rate, error
rate and 95th-percentile latency per operation. These numbers are not computed from stored traces —
they come from *every* span, before sampling decides what to keep
([metrics-and-monitoring.md](metrics-and-monitoring.md)).

The same data is in Prometheus:

```bash
uv run platformctl ui prometheus
```

Try these queries at `http://127.0.0.1:9090/graph`:

```promql
# Requests per second handled by OrderService, by operation and status
sum by (span_name, http_response_status_code) (
  rate(traces_span_metrics_calls_total{service_name="order-service", span_kind="SPAN_KIND_SERVER"}[5m]))

# How many traces each sampling policy kept
sum by (policy) (otelcol_processor_tail_sampling_count_traces_sampled{sampled="true"})
```

## Step 5 — Run an experiment

Now let the platform break something on purpose. In `payment-retry`, PaymentService records the
payment but delays its reply until after OrderService has given up waiting. OrderService retries —
and the question is whether the customer is charged twice.

```bash
uv run scenarioctl run payment-retry
```

The run takes about a minute; most of it is waiting for the Collector's sampling decision. The
verdict:

```text
==> Run 20260918T001359Z-payment-retry-cd2d: PASSED
    requests: 4 {201: 4}; orders read back: 4
[ OK ] [application] HTTP statuses: 201x4
[ OK ] [application] order states: Completedx4
[ OK ] [application] payment authorizations: 4 orders with exactly 1 authorization(s)
[ OK ] [telemetry] trace integrity: 4 trace(s) as expected
[ OK ] [telemetry] kubernetes metadata: 4 trace(s) as expected
[ OK ] [telemetry] correlation: 4 trace(s) as expected
[ OK ] [telemetry] sensitive data: 4 trace(s) as expected
[ OK ] [telemetry] retry attempts: 4 trace(s) as expected
[ OK ] [telemetry] idempotent replay: 4 trace(s) as expected
[ OK ] [telemetry] accumulated latency: 4 trace(s) as expected
[ OK ] [telemetry] state events: 4 trace(s) as expected
```

Reading it from top to bottom:

1. **Application layer.** Four orders, all completed, and the payment ledger — read directly from
   PaymentService — holds exactly one authorization per order. No double charge.
2. **Telemetry layer.** Each of the four stored traces is complete and correctly attached; every span
   carries correct Kubernetes metadata and the request's correlation ids; no secret appears; the
   payment step shows **two** numbered attempts; the second attempt was answered as an
   **idempotent replay**; and the payment step accounts for most of the order's time.

In other words: the application behaved correctly, *and* the telemetry tells that story correctly.
The run record with every request and check is in `.runs/<run id>/record.json`.

## Step 6 — Look at a failed order

```bash
uv run scenarioctl run payment-timeout
```

This time PaymentService never answers. Each order fails with `504`, and the verdict shows three
payment attempts, the compensation steps, and one extra line:

```text
[ OK ] [telemetry] retry attempts: 3 trace(s) as expected
[ OK ] [telemetry] gateway span gap (known Kong 3.9 limitation): 3 trace(s): Kong answered a 5xx
       upstream response with a new balancer span, so OrderService's parent span id is never exported
```

The last line is a *finding*, not a failure. Kong 3.9.3 has a defect: when the upstream answers with
a 5xx status, it exports a different span than the one it announced to OrderService. Open one of these
traces in Jaeger and you will see OrderService's span detached from Kong's. The check recognises this
exact pattern, accepts it, and reports it so that nobody mistakes it for a platform bug — any
*other* broken link would still fail ([known-limitations.md](known-limitations.md)).

## Step 7 — Watch the edge defend the platform (optional)

```bash
uv run scenarioctl run kong-rate-limit   # 120 simultaneous orders against a limit of 30/s
uv run scenarioctl run auth-denied       # missing, forged and insufficient tokens
```

Both show requests being refused *before* any business logic runs — and, importantly, show that
every refused request is still counted in the metrics even though most of their traces are never
stored.

## What you have seen

- One request produces one trace that starts at the gateway and names every pod it touched.
- The Collector keeps the interesting traces and counts everything.
- Experiments inject real failures, restore the platform, and then prove that the telemetry matches
  what happened — including an honest report of a known third-party defect.
